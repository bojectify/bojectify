## Commands

All `pnpm`/`pnpx` run **inside the dev container** via host shims at
`scripts/host-shims/` (supply-chain hardening — dependency code never touches
host secrets). Call `pnpm` normally; routing is transparent. See the
dev-container design in `boject-cms-internal`.

- `pnpm dev` — Next dev server on http://localhost:3001
- `pnpm build` — production (standalone) build
- `pnpm typecheck` / `pnpm lint` / `pnpm lint:scss` — static checks
- `pnpm test:unit` — unit tests (Vitest)
- `pnpm storybook` — Storybook on http://localhost:6008
- `pnpm codegen:graphql` / `pnpm codegen:routes` / `pnpm codegen:tokens` — codegen

## Product

Bojectify is a web-based **fitted-furniture builder**. A user supplies measurements for a space; the tool generates fitted drawers and wardrobes, shown on a zoomable 3D artboard (SketchUp / Shapr3D feel) with light in-canvas editing. **Manufacturing output (cut lists, panel schedules, exports) is a core deliverable, not an afterthought.**

## Planned stack

Next.js (React) + react-three-fiber (r3f) + drei + three.js. No CAD/B-rep kernel (OpenCascade.js etc.) — fitted furniture is axis-aligned boxes, so three.js box geometry is sufficient.

## Architecture: data-model-first (the load-bearing decision)

The **source of truth is a parametric data model of plain TypeScript objects**, not the 3D mesh. Everything derives from it:

```
Parametric model (Room → carcasses → panels/drawers/shelves)
        │                         │
   3D canvas (r3f)        Manufacturing output
   renders the model      derived from the model
   + edits write back     (cut lists, schedules)
```

Three layers with strict boundaries — preserve these when adding code:

- **Data layer** (`model/`, pure TS, no three.js): `types.ts` (`Room`, `Carcass`, `Panel`, `Drawer`, `Shelf`), `generate.ts` (`generateModel({ room, config })`, currently a placeholder), `cutList.ts` (`generateCutList(model)`, a pure function).
- **Render layer** (r3f components, read-only over the model): `<SceneCanvas>` plus `<Carcass>`/`<Panel>`/`<Drawer>`/`<Shelf>` rendering model nodes as box geometry + edges + labels.
- **Interaction layer**: selection via raycasting, and drag/resize handles that **write changes back into the parametric model**, which then re-renders. The model always stays the source of truth.

**Two rules that follow from this and must not be broken:**

1. **Cut lists / manufacturing numbers are computed from the data model, never read back from mesh geometry.** Reading geometry reintroduces floating-point error; the whole point is exact numbers. `generateCutList(model)` must depend only on the data layer.
2. **The data layer has zero knowledge of three.js.** The render layer reads the model and emits edit intents; manufacturing output depends only on the data layer. This keeps the data/cut-list layer unit-testable in isolation and the render layer testable via component tests.

## Next.js integration constraint

The 3D canvas must be a **client component** (`"use client"`) and **dynamically imported with SSR disabled** (`next/dynamic` with `{ ssr: false }`) — three.js cannot render server-side. All other routes (CMS pages, measurement forms, marketing) remain normal SSR'd Next routes.

## Build phasing

1. Static schematic render — model types + a hand-built sample model → r3f scene with orbit/zoom and dimension labels.
2. Cut list — `generateCutList(model)` + a panel-schedule view (validates the data-model-first approach end to end).
3. Light editing — selection + drag/resize handles writing back to the model.
4. Generation engine integration — the real measurements→layout engine.

## Out of scope here

The **parametric generation engine** (raw measurements → manufacturable layouts: clearances, standard panel sizes, hardware constraints, optimisation) is a separate sub-project with its own spec/plan/build cycle. The canvas is deliberately built against hand-made sample models first, treating `generateModel` as a black box.
